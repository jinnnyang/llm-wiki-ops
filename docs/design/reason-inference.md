# llm-wiki reason 推理层设计方案：四种推理 × 时效治理

> 状态：已定稿（设计对话成果）
> 日期：2026-08-03
> 前序文档：`agent-layer.md`（reason agent 基础框架）

## 1. 背景与动机

llm-wiki 目前主要处理**事实性、表面的知识图谱**：实体页、wikilink、元数据。reason agent（`src/agent/reason.ts`）的 mission（hidden connections / knowledge gaps / patterns / anomalies）已经隐含了推理的输出目标，但没有方法论约束——LLM 自由发挥，质量随机。

本方案的目标：让 `llm-wiki reason` 能进行**真正的推理**，覆盖人类智能的四种推理形式（出自对"人类智能：有关推理、逻辑、因果、预测、学习、算法、想法与一切"一文的概念映射）：

| 推理 | 方向 | 性质 | 在 wiki 中的角色 |
|------|------|------|------------------|
| 演绎 | 一般→特殊 | 精确逻辑，前提真则结论必真 | **验证器**，唯一能产出 `confidence: high` |
| 归纳 | 特殊→一般 | 经验性，为演绎提供前提 | 从同类实例提炼规则页 |
| 类比 | 特殊→特殊 | 抽象外推，提供视角与启发 | **不产出结论**，只产出可验证的预测 |
| 溯因 | 特殊→解释 | 长连接、闪念洞见 | 由异常触发，产出假设 |

设计哲学：**不是四个并行工具，而是一个循环**；不是让概率性推理"变对"，而是**产出分级 + 证据链 + 可证伪**——wiki 已有的 `confidence` / `contested` / `status` 三件套正好承接。

## 2. 四种推理的流程协议

### 2.1 演绎（deduction）：规则 + 实例 → 必然结论

唯一能保证正确的流程，也是其他三种推理的验证器。

```
① 定位规则    read_graph(query/type) 找一般性陈述
              （概念页里的 "X 类都有 P"、因果边 A→B）
② 匹配实例    找满足规则前提的具体节点（type/tag/is_a 匹配）
③ 前向应用    规则套实例 → 结论
④ 一致性检查  结论是否与目标节点现有内容、contradictions 字段冲突
⑤ 输出        结论 + 推导链（规则页 → 实例页 → 结论）
              前提都 high → 结论可写 high；冲突 → 标 contested
```

依赖有类型的边（`is_a` / `causes`，见 §3）。无类型边只能确认"连接存在"，不能用于演绎前提。

### 2.2 归纳（induction）：同类实例 → 一般规则

```
① 采样        read_graph(type/tag filter) 收集同类节点（≥3 个）
② 对齐        get_node 逐个读，提取共同属性/关系
③ 提出概括    归纳共性 → 草拟一般规则/概念页
④ 证伪尝试    反向搜索反例：满足条件但不符合结论的节点  ← 关键步骤
⑤ 输出        新概念页 + confidence: low/medium + 证据实例清单
              有反例 → 规则加边界条件（这是归纳真正的价值）
```

归纳产出的规则是未来演绎的**前提**（对应原文"归纳为演绎提供前提"）。

### 2.3 类比（analogy）：结构映射 → 可验证的启发

类比**不产出结论**，只产出"值得验证的预测"。工程上强制体现这一性质。

```
① 锚定        目标节点（待理解的事物）
② 候选召回    结构相似节点：tag 重叠、邻域形状相似（get_edges 对比）、
              source overlap（metrics 已有）
③ 结构映射    LLM 判断是否"形式不同逻辑相同"：
              A 的邻域边 ↔ B 的邻域边 逐一对应
④ 输出        类比边 + 映射表，显式标 heuristic
              强制句式："若类比成立，则 X 应当成立" → X 交给演绎验证
```

### 2.4 溯因（abduction）：异常 → 最佳解释

由**异常**触发，不是由 query 触发。置信度最低、价值最高。

```
触发源：contested 矛盾 / 被引用但缺页 / 孤立簇 / 与现有模型不符的新事实
      （均为纯代码可扫描的信号）

① 界定异常    观察到了什么，与哪些现有节点/边不兼容
② 候选生成    大范围搜索：跨簇 BFS、共享 tag/source 的"跳跃"、web_search
              （即"长连接"——允许跳出局部邻域）
③ 解释评估    每个候选解释的融贯度 = 解释的观察数 + 兼容节点数 − 矛盾数
④ 输出        假设节点（status: hypothesis）+ 它解释了什么
              硬性要求：假设必须能生成可演绎验证的预测，否则不收录
```

### 2.5 四种推理的循环

对应原文的数学推理链（提问→猜想→尝试→验证→反思）：

```
异常/观察 ──溯因──→ 假设 ──类比──→ 视角/候选
    ↑                              │
    │                            归纳（从支持实例中强化）
    │                              │
  新异常 ←──演绎──→ 可检验预测 ──→ check agent（已有：CORRECT/UNCERTAIN/WRONG）
```

已有的 `check` agent 就是演绎验证步骤，循环不用从零建。

### 2.6 置信度分级约束

- LLM 真正能保证正确的只有演绎。归纳/类比/溯因本质是概率性的。
- 四种推理的输出强制走已有置信度字段：
  - 演绎（前提均 high）→ `confidence: high`
  - 归纳 → `confidence: low/medium` + 证据实例清单
  - 类比 → 边标记 `heuristic`，不落结论
  - 溯因 → `status: hypothesis`，必须附带可演绎验证的预测
- 事实变化检测与 `as_of` 机制见 §4。

## 3. 基础设施一：typed edges（有类型的边）

### 3.1 问题

wikilink 语法没有位置放类型——`[[page]]` 只表达"这里有个连接"。但演绎和溯因都依赖**有类型的关系**（`is_a` / `causes` / `contradicts`）。没有类型，推理退化成"LLM 阅读理解"。

### 3.2 方案：载体分工

| 载体 | 职责 | 类型信息 |
|------|------|----------|
| 正文 wikilink | 人类可读的连接，Obsidian 图谱渲染 | **永远无类型，不改** |
| frontmatter `related[]` | 机器可读的边元数据 | **类型放这里** |

wikilink 只回答"边存在吗"，frontmatter 回答"这条边是什么"。类型是**边的属性**，不是载体的属性——不发明 wikilink 类型语法（`[[causes→y]]` 之类会破坏 Obsidian 解析）。

### 3.3 数据格式

`related` 条目从纯字符串扩展为 `string | {slug, relation}`，向后兼容：

```yaml
related:
  - attention-mechanism            # 旧格式：无类型，默认 "related"
  - slug: transformer-architecture
    relation: is_a
  - slug: rnn
    relation: superseded           # 新格式：带类型
```

- 旧的 1000+ 页全部不动，它们的边永远是"无类型连接"——**永久状态**，不是待清洗的债。
- `addEdge(source, target, relation?)`：正文照旧写 wikilink，frontmatter 写带类型条目；slug 已存在为纯字符串时原地升级成对象。幂等性不变。
- 图构建时解析对象条目，`GraphNode.related` 带出 relation；纯字符串解析为 `relation: undefined`。

### 3.4 类型词表：开放 + 推荐（不做封闭 enum）

推荐最小集（写进 SCHEMA / prompt）：

| relation | 语义 | 服务于 |
|----------|------|--------|
| `is_a` | 类属 | 演绎 |
| `instance_of` | 实例 | 归纳的证据 |
| `causes` | 因果 | 溯因/演绎链 |
| `contradicts` | 矛盾 | 溯因触发器 |
| `explains` | 解释 | 溯因产物 |
| `superseded_by` | 被取代 | 时效治理（§4） |
| `related` | 默认兜底 | — |

词表外的类型：警告不拒绝（消费方是 LLM，读得懂）。

### 3.5 方向成为一等公民

有类型的关系天然有向（A causes B ≠ B causes A）。frontmatter 写在 A 页、条目指向 B，即 A→B——现有"边属于谁的 frontmatter"语义正好承接，不用新机制。对演绎的因果链追踪是免费升级。

### 3.6 诚实的边界

改完后图里大部分边仍无类型。四种推理流程必须按"**无类型边 = 连接存在、类型未知**"设计。类型系统**增量生长**：推理 agent 每跑一轮，typed 子图扩大一点，推理能力随之增强（正反馈，但第一天体验偏弱）。

### 3.7 改动范围

`types.ts`（related 条目类型）→ `io/frontmatter` 解析/序列化 → `edge-ops.ts` + `addEdge` 签名 → 图构建解析 → MCP `add_edge` 工具加 `relation` 参数。均为现有模块的小扩展，不动双载体模型。

## 4. 基础设施二：时效治理（as_of + checked + 退避调度）

### 4.1 问题

世界是动态的，任何固有知识都可能过期失效。推理必须有时效维度。

**否决的方案**：把 `created` 改成"事件发生日期"。理由：

1. `created`/`updated` 已在干活（lint 过期检测、index 排序、溯源），覆盖即丢失页面维护时钟。
2. 很多概念没有发生日期（"贝叶斯推理"发生在哪一天？），强制填会导致 LLM 编造年份——引入新的幻觉类别。
3. 发生日期解决不了真正的问题："二战 1945 年结束"永不过期；真正过期的是**状态性事实**（"X 是 CEO""现行政策是 P"）。过期问题的本质不是"何时发生"，而是"**何时成立**"。

### 4.2 方案：双时钟，新增两个字段

```yaml
created: 2026-08-03   # 页面时钟：wiki 何时建立这页（不变，溯源用）
updated: 2026-08-03   # 页面时钟：任意编辑（保留，给 lint 用）
as_of:   2020-06      # 事实时钟：这页描述的状态在何时成立 / 事件发生时点
checked: 2026-08-03   # 验证时钟：上次事实校验（check agent 专用）
```

`as_of` 一个字段覆盖两种语义：

| 页面类型 | `as_of` 含义 | 举例 |
|----------|--------------|------|
| 事件页 | 事件发生日期 | "某政策发布" → 发布日 |
| 状态页 | 事实成立的截止时间点 | "某公司 CEO 是张三" → 信息核实的时点 |

### 4.3 为什么单独加 `checked`，不直接用 `updated`

调度若看 `updated`：改个错别字也会 bump `updated`，调度器误以为"刚验证过"，把检查推迟——验证机制被无关编辑悄悄破坏。因此：

- 调度只看 `checked`（缺失时回退 `updated`）。
- check agent 确认无变化时只动 `checked` 一个字段。

### 4.4 `as_of` 提取规则：只提取，不编造

1. 原文明示了时点（"截至 2024 年 Q3""2026 年发布"）→ 用它；
2. 原文没提 → 用**来源的发布日期**（`raw/` frontmatter 的 `ingested` / 文章自带日期）；
3. 两者都没有 → **留空**。

留空是合法状态。lint 提示"易变主题（`market` / `policy` 类 tag）却没有 `as_of` 的页面"值得人工看一眼——指导，不是硬卡。

### 4.5 调度：指数退避

**核心洞察**（讨论中的修正）：触发检查的时钟不是"事实年龄"，而是"上次验证时间"。已验证的信息没必要短期内重复验证；同时，**`as_of` 与 `checked` 的间隔（考验时长）越久，说明事实经历了更久的历史考验，下一次触发校验的间隔也越久**。

$$\text{next\_interval} = \text{clamp}\Big(\frac{\text{checked} - \text{as\_of}}{12},\ \text{下限：T<1 个月时每周},\ \text{上限 3 年}\Big)$$

校准验证（与讨论中给出的三个例子完全吻合）：

| 考验时长 T = checked − as_of | T/12 | 实际调度 |
|------------------------------|------|----------|
| < 1 个月 | — | **每周检查** |
| 1 年 | 1 个月 | 每月查 |
| 10 年 | 10 个月 ≈ 每年 | 每年查 |
| 100 年 | 8.3 年 → 触顶 | 每 3 年查 |

三个设计优点：

- **无状态**：不需要存"下次检查日期"，任何时刻从两个日期现算。markdown 系统没有调度器状态，正合适。
- **自动变稀**：每次检查通过，`checked` 前进、`as_of` 不动，考验时长自然增长，间隔自动拉长——退避行为从日期里自己长出来。
- **公理自动免检**：贝叶斯定理 `as_of: 1763` → 考验 260 年 → 触顶 3 年一查。提取不出历史日期的页面回退到来源日期，间隔偏短——**安全方向的误差**（多查无害，漏查有害）。

**涌现性质：事实一变，退避自动重置**。修正 `as_of` 到新事实成立时点后，考验时长归零，刚变过的事实立刻回到高频观察区——最近变过的东西最不老实，该盯紧。

### 4.6 事实变更协议

check 发现事实变化时（根本性结论反转、结论没变但成因截然不同等）：

1. 修正正文内容；
2. `as_of` 重置为**新事实成立的时点**（退避自动重置）；
3. 节点末尾追加变更记录（固定一节，既是人类审计，也是溯因推理的素材）：

```markdown
## 变更记录
### 2026-08-03 市场份额修正
- 旧：30%（as_of 2020-06）→ 新：12%（as_of 2025-12）
- 原因：XX 市场重组，原统计口径失效
- 来源：^[raw/sources/...]
```

### 4.7 与已有机制的协同

- **`status: invalidated` + `superseded_by`**（purge agent 已有）：退避扫描产出"到期清单"（类似 `purge --stale-before`，**纯代码零 LLM**），check agent 消费；`superseded_by` 记录取代关系。
- **防误判矛盾**（隐藏的大收益）：A 页 `as_of: 2020` 说"市场份额 30%"，B 页 `as_of: 2025` 说"市场份额 12%"——朴素对比会标 `contradictions`，但有了时间轴，reason agent 能识别这是**演化**而非**矛盾**，应建 supersession 链而不是打 contested。
- **推理 agent 已注入 `Today's date`**（loop.ts 现有机制），消费 `as_of` 不需要新工具，只需 prompt 规则。

### 4.8 诚实的边界

页面级 `as_of` 是粗粒度的——一页可能混着永不过期的定义和易变的状态句。逐句时间标注（双时态数据库）对 markdown wiki 是过度设计，先用页面级，不够再往下走。

### 4.9 改动范围

`types.ts` 加字段 → `scanWiki` / `getNode` / MCP `read_graph` 透出 → ingest agent prompt 加 `as_of` 提取规则 → check agent prompt 加"只更新 `checked`"与变更协议 → reason agent prompt 加时效推理规则 → 新增退避扫描（纯代码，算到期清单）。

## 5. 设计全貌与实现顺序

四块拼图：

1. **typed edges**：`related` 条目支持 `{slug, relation}`，开放词表 + 推荐集，正文 wikilink 不动
2. **`as_of`**：事实时钟，只提取不编造，可留空
3. **`checked` + 退避公式**：纯代码扫描算"到期清单"，check agent 消费
4. **变更协议**：末尾变更记录节 + as_of 重置 → 退避自动归零

四种推理流程（§2）在这些基础设施之上跑。

建议实现顺序（讨论中确认）：

1. **typed edges**（缺口，其他推理的地基）
2. **演绎协议**（验证器）
3. **溯因**（触发源最容易检测：contested / 孤儿 / 缺页都是纯代码扫描）
4. **归纳**
5. **类比**（最依赖候选召回质量，而召回质量依赖前面积累的 typed edges）

时效治理（§4）可与 1-2 并行落地，因为它是独立的基础设施。
