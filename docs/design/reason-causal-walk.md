# llm-wiki reason 因果漫游设计方案：推理即漫游 + 验证

> 状态：待评审（设计对话成果）
> 日期：2026-08-03
> 前序文档：`reason-inference.md`（四种推理 × 时效治理，已定稿）

## 1. 背景与动机

需求起点：一个运行在图上的智能体，根据输入和现状在图上漫游，**走过的路径就是因果链条**；如果走过的节点形成环，则形成"因果闭环"（feedback loop）。在经济分析 wiki 里，闭环是真正有洞察价值的结构——猪周期、价格-产能循环、投资过热周期，全是 feedback loop。

设计对话中想法经历了一次收敛：

| 阶段 | 想法 | 结论 |
|------|------|------|
| v1 | 专用漫游循环：代码管路径状态、环检测，LLM 只管下一步决策 | 过度设计——agent 调用轮数天然是深度限制，再写状态机是重复造轮子 |
| v2（定稿） | **扩展 reason agent**：推理本身就是漫游 + 因果验证，路径通过结构化报告暴露 | 零新模块，dry-run/熔断/前缀容错全部白拿 |

核心张力：**图上的边 ≠ 因果关系**。这个 wiki 的存量边绝大多数是无类型 wikilink（typed edges 刚落地，存量页面几乎没有 `causes`）。如果漫游只是"沿边走"，走出来的顶多是相关链。这反而定义了功能的真正形态：**漫游本身就是因果验证过程**——每一步不是查边，而是 LLM 读了当前节点内容后判断"下一跳是否构成因果"并给出证据。链条的因果性是一步步被论证出来的，不是从图结构里读出来的。

## 2. 漫游协议

不新建 agent，reason 的四种推理循环（`reason-inference.md` §2）就是漫游引擎，补一节操作协议：

```
每一步的结构化动作：
① 读当前节点   get_node 读全文（不是只查边）
② 枚举候选     get_edges 列出相连节点
③ 逐条判断     对与本次推理目标相关的每条关系：真因果 / 伪因果 / 存疑
                （不是对每一个关系都判——枢纽节点几十条边，全量验证会烧光迭代轮数）
④ 记录路径     每一跳必须写入报告：从哪到哪、判定、证据摘录、置信度
⑤ 继续/停止    沿确认的因果边前进；死胡同/达到深度/链条自然结束则停
```

- **深度限制**：agent 调用轮数（默认 30）天然封顶，不另设 max-depth 参数。
- **自主裁决**：轮数限制内，漫游的**启动-经过-终止由 agent 自己决定**，仅通过提示工程软约束，不加任何代码层控制。agent 自行判断：目标是否完成、因果逻辑链是否闭合。如无必要，勿增实体。
- **状态机只当镜子，不当缰绳**：可以引入轻量状态（当前所在节点、已走路径、已访问集合），但唯一目的是**让 agent 知道自己走到哪儿了**，避免原地打转或重复验证。状态只读回给 agent，绝不用于 gating、强制终止或驳回动作——绊手绊脚的状态机比没有更糟。
- **预算可见**（2026-08-03 真实运行教训）：首次漫游在 600s/29 轮被静默超时处决，agent 至死不知道自己有预算，29 轮探索零产出。修复：user message 注入预算数字（迭代数 + 分钟数）+ prompt 加预算纪律（预留最后 20% 写报告，"浅而完整的报告 > 深而超时零产出"）。这是提示工程软约束，不加代码层软终止——符合镜子原则：agent 看见墙，自己决定何时收口。
- **路径暴露**：不需要状态机——推理报告强制包含逐跳链条（每跳：节点、判定、证据摘录），路径自然就是报告主干。
- **闭环检测**：报告中若路径重访节点，agent 须复核环上每一跳的方向性是否仍成立，确认后标记为因果闭环。假环（有一跳不构成因果）不算。
- **选边纪律**：只验证与本次推理目标相关的关系，其余不碰。这是指导不是禁令——agent 根据目标自行取舍。

## 3. 反幻觉因果：三层纪律

幻觉因果的根源是 LLM 把"文本共现 / 图上相连"当成"导致"。对抗它不靠一句"要严谨"，靠可执行的检验程序。

### 3.1 第一层：证据锚定（跳的时候就防）

每一跳的因果判断必须引用当前节点内容里的**具体原文摘录**作为证据。"感觉相关"不算。无类型 wikilink 只能当候选线索，永远不能直接当因果依据（复用 `reason-inference.md` 的既有规则：演绎前提必须是 typed edges）。

### 3.2 第二层：因果三检验（真/伪判定的操作规程）

对每条候选因果关系过三道检验，任一不过即非真因果：

| 检验 | 内容 | 失败信号 |
|------|------|----------|
| 时序检验 | 因的 `as_of` 不得晚于果的 `as_of` | 果先于因。`as_of` 缺失时不许编造日期，标注"时序不明"存疑处理 |
| 机制检验 | 文本里是否描述了 A→…→B 的传导机制 | 只有 A、B 共同出现而无机制 = 相关不是因果。机制是幻觉重灾区，优先用 web_search 找外部依据（见 §6） |
| 反例检验 | 在图里主动找"A 出现但 B 没出现"的实例 | 找到反例 → 降级（复用归纳的证伪步骤） |

### 3.3 第三层：输出纪律（三值判定）

真/伪二分**不采纳**——强行二分会逼 agent 把证据不足的边判成"伪"，产出一堆武断的辨析页，这本身就是一种幻觉。"存疑"必须是一等公民：

| 判定 | 动作 |
|------|------|
| 真因果（三检验全过） | `add_edge(relation="causes")`，context 放证据摘录 |
| 伪因果（任一检验不过） | 建辨析页：记录"为什么看似因果、实际错在哪"（comparison 类） |
| 存疑（证据不足） | 不写边、不建页，标 `status: hypothesis` 留在报告里 |

## 4. reason 产出的页面类型

漫游与四种推理会产出五类页面。**不新建任何目录**——全部由现有 type 承接（见 §5），状态归 frontmatter 不归目录。

| 页面 | type | 来源 | 说明 |
|------|------|------|------|
| 查询回答 | `query` | 用户查询的直接回答 | 现有约定，queries/ 已有几十页佐证 |
| 辨析页 | `comparison` | 伪因果判定 | 两个候选解释的对比辨析，记录证伪过程 |
| 概念/规则页 | `concept` | 归纳产物 | 从 ≥3 实例归纳的一般规则，是后续演绎的前提 |
| 假设页 | `concept` + `status: hypothesis` | 溯因产物 | 必须含可演绎检验的预测；验证后升级或改判 |
| 因果链/闭环记录 | `synthesis` | 漫游产物 | 逐跳路径 + 证据 + 置信度 + 是否闭环。边只能表达"A→B 存在"，表达不了逐跳证据，链条页补这个缺口 |

明确不产出的：

- **知识缺口页**——只标记不创建。没有来源支撑的内容就是编造，内容补充是 ingest 的活（它读真实来源）。reason 的职责到"发现缺口"为止。
- **时序变更记录**——不是新页面。`as_of` 演化在节点内追加 change record（`reason-inference.md` §时效规则）。

统一元数据纪律（五类共用）：

- `status`: hypothesis / contested / established，随验证生命周期流转
- `as_of`: 事实时钟照章走（`reason-inference.md` §4）
- `related[]`: 必须反向链回所有被引用的节点——辨析页链回它辨析的两个节点，链条页链回路径上所有节点。这样它们既是页面也是图的连接点，scan_freshness 和机械遍历都能覆盖。

## 5. 目录设计：TYPE_DIR_MAP 足够

llm-wiki 通过目录分类节点，机制是 `TYPE_DIR_MAP`（`src/types.ts`）：**type 决定目录**（`entity→entities/`、`concept→concepts/`、`query→queries/`、`comparison→comparisons/`、`synthesis→synthesis/`），未知 type 回退 `wiki/<type>/`（`node-ops.ts typeDir()`）。

四类新页面的映射在 §4 表中已给出，全部落在现有目录。**一个关键设计判断：不为"假设"新建目录**——目录表达知识本体（这是什么东西），`status` 字段表达生命周期（它处于什么阶段）。混在一起会让目录随验证状态来回搬家。这和 `as_of`/`checked` 的分工一致：时钟归 frontmatter。

## 6. 工具缺口：add_node 与 write_file 绕过

### 6.1 事故复盘

实测中 reason 把查询回答写进了 `wiki/synthesis/中国经济面临的挑战与发展路径.md`——应该是 `queries/`。查证：

- `wiki/synthesis/` 实际为空，dry-run 没有写盘（dry-run 对 `write_file`/`edit_file` 也拦截，`safety.ts WRITE_TOOLS`）
- 但机制问题是真的：reason 的 MCP 写工具只有 `add_edge` + `update_node`，**没有 `add_node`**
- 本地工具 `write_file` 对所有 agent 开放（`tools.ts`）

模型想"创建页面"时唯一路径是 `write_file` 直接写文件——**绕过了 type→dir 系统**，目录位置全靠模型自由发挥。选 synthesis 不是分类错误，是它根本没有分类机制可用。

### 6.2 write_file 建页面的四个连带伤害

1. frontmatter 全手写，容易漏 `type` / `as_of` / `related`
2. index.md 不会更新（现状：index.md 的 Queries/Synthesis 段落为空）
3. 没有 slug 冲突检测
4. content 里的 wikilink 不会自动同步进 `related[]`

### 6.3 修复

不限制 `write_file`（模型偶尔需要自由写文件），给正路：

1. `REASON_WRITE_TOOLS` 加 `wiki.add_node`（research agent 已有先例）
2. prompt 加指导（不是禁令）：创建 wiki 页面一律用 `add_node`（自动 frontmatter / 目录 / index / related 同步），`write_file` 只用于非页面文件

## 7. web_search 的角色

reason 已具备 web_search：`reason.ts` 创建本地工具时传 `{ webSearch: true }`，`loop.ts` 把 `localTools.definitions` 全部并入暴露给 LLM。前提条件：`.env` 有 `TAVILY_API_KEY`（`tools.ts` 按此条件注册）。

对照三检验的定位——搜索不是"扩大知识面"，是**给机制检验提供锚点**，恰好打在幻觉因果最容易发生的地方：

| 检验 | 图内工具 | 搜索价值 |
|------|----------|----------|
| 时序 | 够（as_of 比对） | 补充：wiki 没记日期时搜事件时间辅助判断，但搜来的日期只作推理依据标注来源，不写进 as_of |
| 机制 | **不够** | 最弱一环。外部来源提供真实机制描述或反驳，压制编造的传导路径 |
| 反例 | 基本够 | 先图内找（便宜、可引用），图内找不到再搜外部 |

引用纪律（与证据锚定对称）：搜索结果是**外部线索**，不是 wiki 事实。写入 wiki 的每条信息必须标注来源 URL；搜索结果与 wiki 内容冲突时，按 `as_of` 时效规则判断谁更新，而不是默认信搜索。

## 8. 实现范围

全部改动收敛为 **reason.ts 单文件扩展**：

1. `REASON_WRITE_TOOLS` 加 `wiki.add_node`
2. prompt 加"因果漫游与验证"一节：逐跳证据强制 + 三检验 + 三值判定 + 辨析页指引 + 选边纪律
3. prompt 加页面产出指引：五类页面的 type 选择 + status/as_of/related 元数据纪律 + add_node 优先
4. 报告格式加"因果链条"主干（逐跳路径）+ "伪因果辨析"清单
5. web_search 使用纪律写入 prompt

不改动：`loop.ts`（熔断/前缀容错/dry-run 已就绪）、`types.ts`（TYPE_DIR_MAP 不动）、`node-ops.ts`、MCP 层（add_node 已存在）。

测试策略：prompt 改动无单测覆盖，靠真实 wiki dry-run 验证——跑查询回答类 query 确认落 `queries/`，跑因果链类 query 确认三检验输出结构。

## 9. 风险与取舍

- **幻觉因果只能缓解不能根除**：三检验 + 证据锚定压制了大部分，但闭环确认那一步的复核必须严格——环上每一跳方向性都要重新成立。
- **成本**：一跳一次 LLM 调用，1149 页 wiki 上靠轮数限制封顶（默认 30 轮 ≈ 8-10 跳）。
- **先做单起点单链**：多起点、全图扫描不做——闭环是漫游的副产品，跑通了再说。
- **存量边无类型**：漫游前期大量关系只能判"存疑"，这符合预期——漫游即关系富化，走得越多图的因果骨架越完整，后续机械式沿 `causes` 边走（纯代码，不用 LLM）才成为可能。

## 10. 性能：scanWiki 缓存决策

reason 在 1149 页 wiki 上一轮漫游 = 几十次 wiki 工具调用，每次 read 类调用都触发一次 `scanWiki` 全量扫描（findMarkdownFiles + 逐文件 readFile + frontmatter/wikilink 解析）。冷扫描 ~350ms × N 次，成为 agent loop 的主要墙钟开销。

**方案 A′（文件级增量缓存，已实施）**：

- 缓存放 `graph-builder.ts` 模块级（所有 scan 的唯一咽喉），`Map<resolvedWikiDir, Map<absPath, {mtimeMs, size, page}>>`
- 只缓存 `ScannedPage[]`，不缓存 Graph——`buildGraphFromPages` 是毫秒级纯内存操作，缓存它徒增失效复杂度
- **懒失效**：每次 scan 逐文件 stat，mtimeMs+size 一致就复用解析结果，不一致才重读。写路径完全不碰缓存——`writeFileAtomic` 会 bump mtime，所以 read-your-writes 和外部编辑都免费生效
- 纯内存、不落盘、生命周期 = 进程生命周期。崩溃无需恢复，源头永远是 .md 文件
- 多 wiki 隔离靠 `path.resolve(wikiDir)` 做 key；`clearScanCache(wikiDir?)` 手动清理
- 不加 in-flight promise 去重：首次扫描之后全部命中，并发冷扫描窗口极窄，不值得引入实体

**升级触发器**：wiki 超 ~5 万页或冷扫描超 ~10s 时，换 SQLite 持久化索引——只替换 `scanWiki` 内部实现，调用方无感知。
